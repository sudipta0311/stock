# C24: End-to-end tests (Playwright, mobile viewport, real API + Postgres), accessibility scans, load-performance check, CI job

**Plan:** `docs/UPGRADE_PLAN.md` §10 (usability bars: Money Map setup < 7 min, add an FD < 30 s, CAS import < 2 min; LCP < 2.5 s on mid-range Android over 4G; accessibility), §8.1 (360 px, low-end devices). Read `AGENTS.md` first. Builds on every PWA card (C19–C23) and the API.

## Goal
Prove the main journeys work in a real browser against the real API and database, at phone size, accessibly and fast enough.

## Scope

### 1. Harness (`e2e/` at repo root)
- Playwright (`@playwright/test`, latest stable, pinned) in its own `e2e/package.json`. Browsers live in a repo-local folder: set `PLAYWRIGHT_BROWSERS_PATH=.playwright-browsers` (gitignore it). Install **Chromium only**.
- `e2e/setup/start-stack.mjs` (global setup):
  - (a) Using `TEST_DATABASE_URL` (owner), create a fresh schema `e2e_<random>` and run `alembic upgrade head` into it. Create a throwaway LOGIN role with a random password, `GRANT wealth_api` and schema usage. **Drop both in teardown.** This is the C05 test-fixture pattern; AGENTS.md allows it only inside fixtures that clean up.
  - (b) Seed market data for the scenario (a few prices/NAVs/FX/gold rows).
  - (c) Start the API with `uvicorn` (ENV=test, AUTH_MODE=dev, a random `DEV_AUTH_SECRET`, `DATABASE_URL` = the throwaway login + `search_path` option, `ALLOWED_ORIGINS` = the preview origin) on a free port.
  - (d) Build the PWA with `VITE_API_URL` pointing at it and `VITE_AUTH_MODE=dev`, then run `vite preview` on a free port.
  - (e) Mint dev tokens for test users.
- Use the Python CAS test helper to generate the synthetic encrypted NSDL PDF at setup into a temp dir (never committed).
- Projects: `mobile` (Pixel-class viewport 412×915, touch, Chromium) and `narrow` (360×740).

### 2. Journeys (each a spec; use roles/labels, never CSS selectors)
1. **Onboarding (the C28 short path) → first plan:** paste the dev token on `/login`, then:
   - choose "Me and my spouse": self "NRI living in Denmark", spouse "Resident in India"
   - skip uploads and land on the plan
   - count taps from the login to the first plan; assert **≤ 5** (excluding the token paste)
   - then, from Home's optional "Make it more accurate" checklist: new tax regime, expenses `75k`, goal "Child education abroad" USD 50,000 in 2034, risk answers; the plan updates
2. **Add FD in < 30 s:** tiles: tick FD + EPF + Insurance → FD form with `5L`, `7.1`, maturity Mar 2027 (required fields only) → autosaved → "Value today" visible. Measure the time from opening the form to the saved indicator; assert < 30 s.
3. **Quick-add:** "EPF 12L" → form pre-filled → save; "random words" → friendly not-understood hint.
4. **CAS import:** upload the synthetic PDF with the right password → review shows counts → confirm → Money shows the holdings and updated net worth. Measure upload-to-confirmed time (< 2 min). A wrong password shows the friendly message.
5. **Plan and Home:** Plan shows "Your money vs your plan" with text values and the safe-money answer. Its Details sections are closed by default. Home shows "This week" (actions or "Nothing to do this week ✓"), with who acts on each action. Mark one action done and check that it updates.
8. **Shared household (C27c):** the owner invites a partner. The partner's token opens `/join?token=…` and accepts. Both see the same family net worth. A viewer sees "View only" and can't edit.
9. **Usability timings (`docs/usability-script.md` from C28):** time the 5 scripted tasks at the `narrow` project and report them in `out/e2e/usability.json` against their targets. "Find what to do this week" and "find how much should be safe money" must be visible without scrolling on Home/Plan at 360×740.
6. **Isolation:** user B logs in and sees none of user A's data (Money empty, direct navigation to A's asset URL → not found).
7. **Delete account:** Settings → delete → confirm → back at login; the API (via owner connection in the test) shows the user's rows are gone.

### 3. Accessibility
`@axe-core/playwright` on Login, Onboarding (each step), Money, FD form, Import review, Plan, Home, Ideas, Inbox, Settings: **0 serious/critical violations**. Write the full report to `out/e2e/axe.json`.

### 4. Performance check
With Chromium CDP: CPU throttling 4× + a "Fast 4G"-like network profile (latency 150 ms, ~1.6 Mbps down). Load `/` (authenticated, warm API) on the preview build; collect LCP via `PerformanceObserver` and total transferred JS. Assert **LCP < 2.5 s**; report numbers to `out/e2e/perf.json`. If it fails, report it and the biggest chunks. Don't loosen the threshold.

### 5. CI
Add an `e2e` job to `.github/workflows/ci.yml` (on push to main and manual): Postgres service, Python + Node setup, `npx playwright install --with-deps chromium`, run the suite, upload `out/e2e/` as an artifact.

## Out of scope
Fixing product bugs found by e2e beyond small, obvious frontend fixes. Anything bigger: list it in the result file with the failing step, so the reviewer can open a follow-up card.

## Acceptance
1. `cd e2e && npm ci && npx playwright install chromium && npx playwright test` → all journeys pass on both projects (report timing metrics)
2. Axe: 0 serious/critical; perf numbers reported (LCP threshold met, or a clearly documented failure)
3. Python and PWA suites still green; the throwaway DB role and schema are always dropped (verify after a run that no `e2e_*` schema or role remains)
4. `.playwright-browsers/`, `out/` and `e2e/node_modules/` are gitignored
