## Reviewer notes
- Security review:
  - Refresh tokens are stored only as SHA-256 hashes, and the refresh row is locked during rotation.
  - Reuse detection revokes the session and audits it; `ALLOWED_EMAILS` is re-checked on every refresh; responses are `no-store`.
  - `auth_sessions` is a per-login RLS table (FORCE). The `SECURITY DEFINER` lookup only maps a hash to (session, user) and is executable only by `wealth_api`.
  - Google ID tokens are still accepted during the transition.
- Reviewer fixes for real-world use:
  - **Multi-tab and lost-response false theft:** every tab shares the rotating refresh token, so two tabs refreshing at once, or a refresh whose response was lost on mobile data, presented a just-rotated token and revoked the whole session. The server now answers 409 (no revocation) when the previous token is presented within 30 s of rotation; reuse after that still revokes and audits. The PWA serialises refreshes across tabs with the Web Locks API, re-reads the stored token inside the lock, and on 409 retries with a newer stored token if one exists. Server and client tests cover both paths.
